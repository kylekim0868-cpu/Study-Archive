# DFS — 설계 기록

- 풀이 코드: [`05_dfs.py`](../../week3/1.%20basic/05_dfs.py)
- 문제점 기록: [DFS — 문제점 기록](../문제모음집/05_dfs.md)
- 진행 상태: 디버깅 중

## 처음 생각한 흐름

```text
시작 정점 방문 처리
→ 현재 노드와 연결된 이웃 확인
→ 방문하지 않았다면 재귀 호출
→ 방문할 이웃이 없다면 현재 함수 종료
→ 호출 스택을 통해 직전 노드로 복귀
→ 다른 이웃 탐색
```

말로는 흐름을 적었지만 코드로 옮길 때 `visited`의 역할과 현재 정점의 이웃을 꺼내는 방법이 섞였다. 특히 방문 기록을 그래프 크기만큼 미리 만드는 배열로 생각한 것이 첫 번째 패착이었다.

## 디버깅하며 바뀐 생각

### 방문 기록

`visited`는 빈 상태에서 시작하여 실제 방문한 정점을 하나씩 추가한다.

```text
visited가 아직 없다
→ 빈 방문 기록을 한 번 만든다

DFS 함수가 시작된다
→ 현재 정점 start를 방문 기록에 추가한다
```

처음에는 `visited = [start]`로 만들면 된다고 생각했다. 최초 호출에서는 맞아 보이지만, 재귀 호출마다 새로운 리스트를 만들면 이전 방문 기록이 사라진다. 하나의 방문 리스트를 계속 전달하면서 현재 정점만 추가해야 한다.

### 이웃 탐색

처음에는 습관처럼 `range(len(graph))`로 인덱스를 만들었다. 하지만 필요한 것은 전체 정점의 인덱스가 아니라 현재 정점과 직접 연결된 이웃이다.

```text
start = 0 → graph[0]의 이웃 확인
start = 1 → graph[1]의 이웃 확인
start = 2 → graph[2]의 이웃 확인
```

그래서 `graph[start]`에서 이웃 정점 `neigh`를 직접 꺼내야 한다. BFS에서 `current`의 이웃을 확인한 것과 같은 개념이었다.

### 재귀 호출

이웃 `neigh`가 방문 기록에 없다면 `neigh`를 다음 함수의 `start`로 넘긴다. 호출된 함수가 시작되면서 자기 자신을 방문 처리하기 때문에 호출하는 쪽에서는 방문 여부만 확인한다.

## 내가 이해한 재귀 흐름

```text
현재 정점을 방문 처리한다
→ 현재 정점의 이웃을 확인한다
→ 방문하지 않은 이웃을 발견하면 그 이웃으로 깊게 들어간다
→ 더 방문할 이웃이 없다면 현재 함수가 끝난다
→ 호출 스택에 남아 있는 직전 함수로 돌아간다
→ 아직 확인하지 않은 다른 이웃을 계속 탐색한다
```

`visited`가 재귀를 직접 종료시키는 것은 아니었다. 이미 방문한 노드를 다시 탐색하지 않도록 막아주고, 방문하지 않은 이웃이 없어 재귀 호출이 하나씩 끝난다. 마지막 호출까지 끝나 호출 스택이 비면 DFS 탐색도 종료된다.

## 다음 실행에서 확인할 것

- 최초 호출에서만 빈 방문 리스트가 만들어지는가?
- 각 함수가 시작될 때 현재 `start`가 한 번만 추가되는가?
- `graph[start]`의 이웃을 직접 순회하는가?
- 방문한 이웃은 재귀 호출하지 않는가?
- 반환된 리스트가 실제 방문 순서와 일치하는가?

## Flood Fill — 재귀 호출에 무엇을 전달해야 할까?

- 문제: [LeetCode 733. Flood Fill](https://leetcode.com/problems/flood-fill/)
- 오류 기록: [Flood Fill 학습 과정](../문제모음집/05_dfs.md#flood-fill--이게-어떻게-easy-문제일까)

### 처음 생각한 방식

현재 칸을 칠하고 `floodFill`을 상하좌우 좌표로 다시 호출하면 된다고 생각했다. 재귀니까 자기 자신을 호출하는 게 자연스럽지 않은가? 그런데 처음 색을 유지하는 부분에서 막혔다.

함수를 새로 만드는 사고력을 길러야 하나 싶었다. 하지만 먼저 생각할 것은 “다음 호출이 일을 하려면 어떤 정보가 필요한가?”였다. 보조 함수는 그 정보를 전달하는 방법 중 하나다.

### 바뀌는 정보와 유지할 정보

| 정보 | 탐색하면서 어떻게 되는가? |
|---|---|
| 현재 좌표 | 이웃으로 이동할 때 바뀐다. |
| 처음 색 `origin` | 시작 칸에서 정한 값을 유지한다. |
| 새 색 `color` | 처음 전달받은 값을 유지한다. |
| 이미지 | 같은 이미지를 공유하고 칸의 색을 바꾼다. |

예를 들어 처음 호출이 `(0, 0, 1)`이라면 오른쪽은 `(0, 1, 1)`, 그다음은 `(0, 2, 1)`이다. 좌표만 이동하고 처음 색 1은 유지한다. 마지막 칸의 실제 색이 0이라면 원래 색 1과 다르므로 멈춘다.

### 호출 한 번의 역할부터 정하기

DFS 한 번은 현재 칸을 확인하고, 칠할 대상이면 칠한 뒤 이웃에게 같은 일을 요청한다.

```text
현재 좌표가 범위 밖이면 현재 호출 종료
→ 현재 칸이 처음 색과 다르면 현재 호출 종료
→ 현재 칸을 새 색으로 변경
→ 상하좌우 좌표에 같은 탐색 요청
→ 각 호출이 끝나면 호출했던 곳으로 돌아와 남은 방향 탐색
```

이미지는 칸 자체가 정점이고 상하좌우가 이웃이다. 별도의 인접 리스트를 만들지 않아도 좌표로 다음 칸을 찾을 수 있다.

### 왜 보조 함수를 만들었나?

문제에서 주어진 `floodFill`의 인자에는 원래 색이 따로 없다. 이 함수를 그대로 재귀 호출하면서 현재 칸에서 원래 색을 다시 구하면 처음 기준을 잃는다. 그래서 초기 준비와 반복 탐색의 역할을 나눴다.

```text
바깥 floodFill
→ 처음 색 저장
→ 새 색과 같으면 image 반환
→ 시작 좌표로 DFS를 한 번 실행
→ 탐색이 끝난 image 반환

DFS
→ 현재 좌표 검사와 색칠
→ 처음 색을 유지하며 다음 좌표로 재귀 호출
```

함수 안에 함수를 만드는 것이 필수는 아니다. 별도 메서드로 만들고 필요한 정보를 전달할 수도 있다. 이번에 생각한 중첩 함수 방식에서는 `image`와 `color`를 바깥 함수에서 참고하고, 좌표와 `origin`은 인자로 전달할 수 있다. 핵심은 함수의 위치보다 처음 색을 어떻게 유지할 것인지다.

### 다음에는 어떻게 설계할까?

바로 코드부터 쓰기 전에 세 문장을 먼저 적어야겠다.

1. 한 번의 호출이 하는 일은 무엇인가?
2. 다음 호출에 어떤 정보가 필요한가? 무엇은 바뀌고 무엇은 유지되는가?
3. 어떤 조건에서 현재 호출을 끝내는가?

그다음 기존 함수의 인자로 필요한 정보를 전달할 수 있는지 확인한다. 부족하다면 인자를 추가하거나 보조 함수를 만드는 방법을 생각한다. 문제에서 정해준 함수의 형식도 지켜야 한다.

Easy라고 해서 나에게도 당연히 쉬워야 하는 건 아니었다. 그렇다고 코드를 따라 완성했다고 이해한 것도 아니다. 다음 복습에서는 완성 코드를 먼저 보지 않고 `[1, 1, 0]`의 좌표와 원래 색이 각 호출에서 어떻게 유지되는지 직접 적어보자.

> 정리 → “함수를 하나 더 만들어야 하나?”보다 “다음 호출에는 어떤 정보가 필요하지?”를 먼저 생각하자.
