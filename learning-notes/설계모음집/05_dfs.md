# DFS — 설계 기록

- 풀이 코드: [`05_dfs.py`](../../week3/1.%20basic/05_dfs.py)
- 문제점 기록: [DFS — 문제점 기록](../문제모음집/05_dfs.md)
- 진행 상태: 디버깅 중

## 처음 생각한 흐름

```text
시작 정점 방문 처리
→ 현재 노드와 연결된 이웃 확인
→ 방문하지 않았다면 재귀 호출
→ 방문할 이웃이 없다면 현재 함수 종료
→ 호출 스택을 통해 직전 노드로 복귀
→ 다른 이웃 탐색
```

말로는 흐름을 적었지만 코드로 옮길 때 `visited`의 역할과 현재 정점의 이웃을 꺼내는 방법이 섞였다. 특히 방문 기록을 그래프 크기만큼 미리 만드는 배열로 생각한 것이 첫 번째 패착이었다.

## 디버깅하며 바뀐 생각

### 방문 기록

`visited`는 빈 상태에서 시작하여 실제 방문한 정점을 하나씩 추가한다.

```text
visited가 아직 없다
→ 빈 방문 기록을 한 번 만든다

DFS 함수가 시작된다
→ 현재 정점 start를 방문 기록에 추가한다
```

처음에는 `visited = [start]`로 만들면 된다고 생각했다. 최초 호출에서는 맞아 보이지만, 재귀 호출마다 새로운 리스트를 만들면 이전 방문 기록이 사라진다. 하나의 방문 리스트를 계속 전달하면서 현재 정점만 추가해야 한다.

### 이웃 탐색

처음에는 습관처럼 `range(len(graph))`로 인덱스를 만들었다. 하지만 필요한 것은 전체 정점의 인덱스가 아니라 현재 정점과 직접 연결된 이웃이다.

```text
start = 0 → graph[0]의 이웃 확인
start = 1 → graph[1]의 이웃 확인
start = 2 → graph[2]의 이웃 확인
```

그래서 `graph[start]`에서 이웃 정점 `neigh`를 직접 꺼내야 한다. BFS에서 `current`의 이웃을 확인한 것과 같은 개념이었다.

### 재귀 호출

이웃 `neigh`가 방문 기록에 없다면 `neigh`를 다음 함수의 `start`로 넘긴다. 호출된 함수가 시작되면서 자기 자신을 방문 처리하기 때문에 호출하는 쪽에서는 방문 여부만 확인한다.

## 내가 이해한 재귀 흐름

```text
현재 정점을 방문 처리한다
→ 현재 정점의 이웃을 확인한다
→ 방문하지 않은 이웃을 발견하면 그 이웃으로 깊게 들어간다
→ 더 방문할 이웃이 없다면 현재 함수가 끝난다
→ 호출 스택에 남아 있는 직전 함수로 돌아간다
→ 아직 확인하지 않은 다른 이웃을 계속 탐색한다
```

`visited`가 재귀를 직접 종료시키는 것은 아니었다. 이미 방문한 노드를 다시 탐색하지 않도록 막아주고, 방문하지 않은 이웃이 없어 재귀 호출이 하나씩 끝난다. 마지막 호출까지 끝나 호출 스택이 비면 DFS 탐색도 종료된다.

## 다음 실행에서 확인할 것

- 최초 호출에서만 빈 방문 리스트가 만들어지는가?
- 각 함수가 시작될 때 현재 `start`가 한 번만 추가되는가?
- `graph[start]`의 이웃을 직접 순회하는가?
- 방문한 이웃은 재귀 호출하지 않는가?
- 반환된 리스트가 실제 방문 순서와 일치하는가?
