## `None`에 `append()`를 호출함

### 오류 메시지

```text
AttributeError: 'NoneType' object has no attribute 'append'
```

처음에는 그래프 크기만큼 방문 배열을 생성해야 한다고 생각했다.

```python
if not visited:
    for i in graph:
        visited.append([None])
```

하지만 최초 호출에서 `visited`는 `None`이다. 아직 리스트가 만들어지지 않았는데 `append()`부터 호출했기 때문에 오류가 발생했다. 빈 딕셔너리에 키를 만들지 않고 `append()`했던 그래프 문제와 비슷했다. 데이터를 추가하려면 데이터를 담아줄 자료구조부터 먼저 만들어야 한다.

또한 `visited`는 그래프 크기만큼 미리 공간을 만드는 배열이 아니었다. 실제로 방문한 정점을 순서대로 추가하는 리스트다.

```text
최초 상태 → []
0 방문    → [0]
1 방문    → [0, 1]
```

## 빈 리스트의 마지막 위치에 값을 대입하려고 함

```python
visited[-1] = start
```

`visited`를 빈 리스트로 만든 직후에는 `-1` 위치도 존재하지 않는다. 기존 위치의 값을 바꾸는 것이 아니라 현재 방문한 정점을 새롭게 기록해야 하므로 `append()`의 역할이 필요했다.

## 현재 정점이 아닌 1번 정점만 확인함

### 당시 코드

```python
for i in range(len(graph)):
    if graph[1][i] not in visited:
```

DFS는 재귀 호출마다 현재 정점이 달라진다. 그런데 `graph[1]`로 고정하면 어디에서 재귀 호출됐든 항상 1번 정점의 이웃만 확인한다.

또한 `len(graph)`은 전체 정점 수지만 `graph[1]`은 1번 정점의 이웃 목록이다. 두 길이가 항상 같지 않으므로 존재하지 않는 인덱스에 접근할 수도 있다.

현재 필요한 것은 그래프 전체의 인덱스가 아니라 `graph[start]`에 들어 있는 이웃 정점 자체였다.

## 방문 처리의 역할을 두 곳에 둘 뻔함

처음에는 이웃을 발견한 쪽에서 `visited`에 추가하고 재귀 함수를 호출하려고 했다. 하지만 각 DFS 함수가 시작될 때 자신의 `start`를 방문 처리한다면 호출하는 쪽에서는 방문 여부만 확인하면 된다.

```text
현재 DFS 함수 → 자신의 start를 방문 처리
반복문        → neigh의 방문 여부 확인
재귀 호출     → 미방문 neigh를 다음 start로 전달
```

방문 처리를 양쪽에서 모두 담당하면 같은 정점을 중복으로 기록할 수 있다. 하나의 동작을 어디에서 책임질지 먼저 정해야겠다.

## 다시 확인할 질문

- `visited`는 미리 크기를 정하는 배열인가, 방문할 때마다 늘어나는 기록인가? A: 방문할 때마다 늘어나는 기록
- `graph`를 순회할 때와 `graph[start]`를 순회할 때 각각 어떤 값이 나오는가? A: Key값 / 배열 안의 이웃 정점 하나씩
- 현재 함수가 방문 처리를 담당한다면 호출하는 쪽에서는 무엇만 확인하면 되는가? A: 이웃이 방문한 정점
- 더 이상 방문하지 않은 이웃이 없을 때 재귀 함수는 어디로 돌아가는가? A: 자신을 호출했던 이전 DFS함수로 돌아간다.

## Flood Fill — 이게 어떻게 Easy 문제일까?

- 문제: [LeetCode 733. Flood Fill](https://leetcode.com/problems/flood-fill/)
- 진행 상태: 설계와 오류 원인 정리. 최종 제출 통과 여부는 아직 확인하지 않았다.
- 연결 기록: [Flood Fill 설계 과정](../설계모음집/05_dfs.md#flood-fill--재귀-호출에-무엇을-전달해야-할까)

재귀함수니까 당연히 `floodFill`을 다시 호출하면 된다고 생각했다. 그런데 함수 안에 새로운 함수를 만들고, 그 함수가 재귀로 동작하고, 좌표로 상하좌우까지 이동해야 했다. 이게 어떻게 쉬운 문제인가? DFS 하나를 배우는 줄 알았는데 함수 구조와 이차원 배열까지 한꺼번에 엉켰다.

### 행과 열, 리스트와 길이가 섞였다

처음에는 아래로 이동하는 좌표를 `(sr-1, sc)`라고 생각했다. 하지만 행 번호는 아래로 갈수록 커진다. 아래는 `(sr+1, sc)`, 위는 `(sr-1, sc)`다. 오른쪽은 열에 1을 더하고, 왼쪽은 1을 뺀다.

범위 검사에서도 `image[0]`과 `len(image[0])`이 헷갈렸다. `image[0]`은 첫 번째 행 자체이고, 그 행의 길이가 열 개수다. 행은 `0 <= r < len(image)`, 열은 `0 <= c < len(image[0])`인지 확인해야 한다. 이 검사는 현재 칸을 읽거나 칠하기 전에 해야 한다. Python에서 음수 인덱스는 뒤쪽 원소를 가리킬 수 있으니 오류가 안 난다고 올바른 좌표인 것도 아니다.

### 원래 색을 저장했는데 왜 다른 색까지 칠할까?

`origin = image[sr][sc]`로 원래 색을 저장했다. 문제는 이 줄을 재귀 호출할 때마다 다시 실행했다는 것이다.

```text
이미지: [1, 1, 0], 시작 위치: (0, 0), 새 색: 2

처음 색 1을 계속 유지 → 마지막 0에서는 멈춘다.
이동할 때마다 원래 색을 다시 저장 → 마지막 칸에서는 origin도 0이 된다.
```

현재 칸의 색을 방금 `origin`에 넣고 두 값을 비교하면 항상 같다. 원래 다른 색이었던 칸을 걸러낼 수 없다. 좌표는 바뀌어야 하지만, 처음 색은 바뀌면 안 됐다.

### 색칠 전과 후의 조건을 혼동했다

현재 칸을 `color`로 칠하고 나서 새 색과 같은지 확인하면 항상 참이다. 반대로 원래 색과 같은지 확인하면, 새 색과 원래 색이 다를 때 거짓이라 이웃 탐색이 막힌다.

필요한 순서는 범위 검사 → 원래 색인지 검사 → 칠하기 → 상하좌우 탐색이었다. 칠하기 전에 대상을 확인했으니 칠한 뒤에 같은 검사를 다시 붙일 필요가 없었다.

색칠은 방문 표시 역할도 한다. 이미 칠한 칸으로 돌아오면 원래 색과 달라서 해당 호출이 끝난다. 단, 처음 색과 새 색이 같으면 이 표시가 남지 않는다. 그래서 탐색을 시작하기 전에 두 색이 같으면 `image`를 반환해야 한다.

### 함수 정의와 실행, 전달값이 섞였다

`dfs`를 정의하고도 처음 실행하는 호출을 빠뜨렸다. `def`로 탐색 방법을 적어두는 것만으로 탐색이 시작되지는 않는다.

세 인자를 받는 DFS에 네 값을 전달하기도 했고, `origin` 자리에 `color`를 넘기기도 했다. 호출할 때는 인자 개수뿐 아니라 그 자리에 어떤 의미의 값이 필요한지도 확인해야 한다.

DFS에서 칠할 대상이 아니면 `return`으로 현재 호출만 끝내면 된다. 바깥 `floodFill`은 문제에서 요구하는 이미지 전체를 반환해야 한다. 같은 `return`이어도 각 함수가 맡은 일이 다르다.
